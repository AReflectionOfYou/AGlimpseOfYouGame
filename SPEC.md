# A Glimpse of You — Build Spec

A local-network picture-guessing game in the spirit of classic face-guessing games, using photos of our own family (and pets). Two players sit together, ask yes/no questions out loud, and each flips down faces on their own device. The conversation is the game; the app is just the board and an honest witness for each player's secret face.

**Name:** A Glimpse of You (part of the A Reflection of You collection). Use this name in the README, page title, web app manifest, and startup banner.
**Repo:** `a-glimpse-of-you` in the A Reflection of You GitHub organization, open source. **No photos are ever committed.** Each family brings their own (section 4).
**Start fresh:** build this in a **brand-new, empty repo** created in the A Reflection of You org. Do not fork, copy, transfer, or migrate the earlier private Family Guess Who repo or its git history, and do not bring over any photos from it, including in `photos/`, test fixtures, sample assets, or screenshots. Old photos stay in the old private repo (or wherever the family keeps them) and are added locally later using the bring-your-own-photos setup. Any test images must be generated by code (as the demo script does), never taken from real photos.
**Network:** local WiFi only. No internet services, no CDNs, no analytics, no external calls of any kind at runtime.

---

## 1. Core concept

- One small server runs on a computer on the home network (a Mac laptop is the expected host).
- Two players open the game in a browser (iPhone, iPad, or laptop) on the same WiFi.
- Both players see the **same faces in the same order**, but each has a **private board**: flips on one device are never shown on the other.
- Each player has a **secret face**, locked in at the start and recorded by the server so it can't be forgotten or changed.
- Questions and the final guess are **spoken aloud**. The app does not adjudicate guesses. A wrong guess just means play continues.
- Photos are **untagged and unnamed**. Interpreting them is part of the fun.

**Important:** the server runs on a computer, not on an iPad or iPhone. The phones and tablets are always just players using Safari. The computer running the server can also be a player through its own browser.

## 2. Tech stack

- **Node.js** (current LTS) server with **Express** for static files and **Socket.IO** for real-time state (its automatic reconnection handles iPads going to sleep and waking up).
- **Plain HTML/CSS/JS** front end, no build step, no framework.
- Socket.IO client and any QR library are served from the local server (from `node_modules`), never from a CDN.
- **sharp** for the photo prep script.
- **node:test** for automated tests.
- Target browsers: iOS Safari (primary), plus desktop Safari/Chrome.

## 4. Themes and photos

### 4.1 Bring your own photos
- The repo ships with **no photos**. `.gitignore` excludes everything under `photos/` except `photos/README.md`, and everything under `incoming/`. This keeps family pictures out of the public repo and out of anyone's fork.
- By default the server reads photos from `photos/` in the repo. A `PHOTOS_DIR` environment variable (or a `photos.config.json` file, also gitignored) can point it at a folder anywhere else, such as a Dropbox or iCloud Drive folder, so the collection can live outside the repo and be shared across machines.
- `photos/README.md` explains in plain words: make one folder per theme, put square photos in it (or use the prep script), restart or refresh setup.
- **First-run experience:** if no themes are found, the setup screen shows a friendly "No photos yet" panel instead of the pickers, with the three steps for adding photos and a note that `npm run demo` will create a sample theme. The terminal startup banner says the same.
- **Demo theme:** `npm run demo` runs `make-demo-photos.js`, which uses sharp to generate about 24 simple, colorful, original images (varied shapes, colors, patterns and a large letter or number) into `photos/demo/`. This lets someone try the game in a minute with no personal photos and no licensing questions. The demo folder is gitignored like every other theme.
- Before any commit, a test (section 11) checks that no image files are tracked under `photos/`.

### 4.2 Themes
- Each subfolder of `photos/` is a **theme**. The display name comes from the folder name (`aunties` → "Aunties", `cousins-2025` → "Cousins 2025").
- An extra built-in theme, **Everyone**, draws from all folders combined. It is listed first.
- Accepted image types: `.jpg`, `.jpeg`, `.png`, `.webp`. Ignore dotfiles and anything else.
- Themes are rescanned when the server starts (and preferably each time the setup screen loads), so adding a folder needs no code changes.
- The same person may appear many times in different photos or outfits. Each image file is one face; no notion of "person" exists in the app.
- Empty theme folders are hidden from the picker.

## 5. Game flow

### 5.1 Startup
Running `npm start`:
- Binds to `0.0.0.0` on port **3000** (overridable with `PORT`).
- Prints a startup banner in the terminal showing the join URL by IP (e.g. `http://192.168.1.42:3000`), the `.local` URL when available (e.g. `http://mikes-macbook.local:3000`), and a **QR code rendered in the terminal**.

### 5.2 Joining
- The first two browsers to connect take **Player 1** and **Player 2** seats.
- Each device gets a seat token stored in `localStorage` (wrap all storage access in try/catch). On reload or reconnect, the device reclaims its seat and its full state is restored.
- A third device sees a friendly "This game already has two players" message.
- Every screen shows a small indicator of whether the other player is connected.

### 5.3 Join screen (shown until both players are in)
Displays, large and clear:
- A **QR code** of the join URL (the primary method; generated locally).
- The **plain URL** as text (the fallback).
- A **Share** button using the Web Share API (`navigator.share`) so the link can be AirDropped or texted from the device. Hide the button if the API is unavailable.
- A short note: "The other player must be on the same WiFi."

### 5.4 Setup screen
Either player may set up the round. Three choices, then **Deal**:

1. **Theme**: a picker of themes (Everyone first, then alphabetical), each showing how many photos it has.
2. **Number of faces**: a selector from **6 to 24**. Presets: 6, 9, 12, 16, 20, 24. Options larger than the chosen theme's photo count are disabled.
3. **Secret faces**: a toggle between **Random** (default) and **Players choose**.

Settings from the previous round are pre-selected. Once one player deals, the other player's setup screen is replaced by the game.

### 5.5 Dealing
- The server randomly selects the chosen number of distinct images from the theme and shuffles their order once.
- Both players receive the **identical ordered list**.
- **Random mode:** the server assigns each player a secret face from the board. The two secrets must be different faces (count is always ≥ 6, so this is always possible).
- **Players-choose mode:** go to the choosing phase (5.6).

### 5.6 Choosing phase (Players-choose mode only)
- Prompt: "Tap the face you want to be."
- Tapping a face opens a large confirmation: the face, plus "Be this one" and "Back."
- Once confirmed, the choice is **locked** and sent to the server. It cannot be changed for the rest of the round.
- Show "Waiting for the other player to choose…" until both have locked in. Both players may choose the same face; that's allowed in this mode.
- Flipping is disabled during this phase.

### 5.7 Playing
- **Tap a face to flip it down; tap again to flip it back up.** A flipped-down tile shows a card back (solid color with a subtle pattern), not a dimmed photo.
- Flips are private. They are sent to the server only so a reloaded device can restore its board; the server never sends one player's flips to the other.
- A small counter shows how many faces you still have up.
- A **"My face"** button in the top bar opens a modal showing your secret face large. It is never shown on the board itself, so an opponent glancing over can't spot it. This modal is also how a player proves the answer at the end: hold up the screen.
- Guessing is spoken aloud. No guess button, no win detection, no scoring.

### 5.8 New Game
- A **New Game** button is always visible during play.
- Tapping it opens a confirmation: "Start a new game? This clears both boards." with **Deal again** (same settings), **Change settings** (back to setup), and **Cancel**.
- Confirming resets the round for **both** players.

## 6. Board layout

The face count is shared; the arrangement adapts to each screen.

- Tiles are **square**. Photos fill the tile with `object-fit: cover`.
- Grid sizing is a pure function in `layout.js`: given the count and the available width and height (after the top bar and safe areas), try every column count from 1 to N, compute rows = ceil(N / cols), tile size = min(width / cols, height / rows) minus gaps, and choose the column count with the largest tile size. Recompute on resize and orientation change.
- The whole board should fit without scrolling. If tiles would fall below roughly 64px, allow vertical scrolling instead of shrinking further.
- Expected results: 6 faces on a portrait phone → 2×3 big tiles; 24 on a portrait phone → about 4×6; 24 on a landscape iPad → about 6×4.
- Preload all board images before revealing the board, so both players don't see faces popping in.

## 7. Mobile and touch details

- Viewport set for no pinch-zoom surprises; `touch-action: manipulation` on tiles to kill double-tap zoom and the tap delay.
- Disable text selection and the long-press image callout on tiles (`-webkit-user-select: none`, `-webkit-touch-callout: none`) so a lingering press doesn't pop up "Save Image."
- Respect safe-area insets (notch, home indicator).
- Works in portrait and landscape.
- Large, kid-friendly tap targets on all buttons. Simple words, minimal text.
- Optional: include a web app manifest and icon so it can be added to the home screen. No service worker needed.

## 8. Server state and messages

The server holds **one game at a time** in memory. Losing it on server restart is acceptable.

State:
- `settings`: theme, count, secretMode
- `phase`: `lobby` | `setup` | `choosing` | `playing`
- `board`: ordered list of image URLs
- per seat: token, connected flag, secret index (or null), set of flipped indices

Each client receives a **personalized** state: the shared board and phase, its own secret and flips, and only the opponent's connection status and whether the opponent has locked in a secret (true/false). **The opponent's secret index and flips must never be sent to the other client.** Add a test for this.

Suggested events (adjust as needed):
- client → server: `join {token?}`, `deal {theme, count, secretMode}`, `chooseSecret {index}`, `flip {index, down}`, `newGame {mode: "again" | "settings"}`
- server → client: `state {…personalized…}`, `full`

The server validates everything (index ranges, phase, locked secrets can't change, count within 6–24 and within pool size).

## 9. Photo prep script

Turns full-size exports from Apple Photos into board-ready images.

**Workflow:**
1. In Photos on the Mac, select the pictures and use **File → Export → Export N Photos** with Kind = **JPEG**. Save them into the repo's `incoming/` folder.
2. Run: `npm run prep -- --theme aunties`
3. The processed images appear in `photos/aunties/` (or the `PHOTOS_DIR` folder). They are **not** committed; back them up however you back up your photos.

**The script:**
- Reads every image in `incoming/` (`.jpg`, `.jpeg`, `.png`, `.webp`, `.heic`).
- `.heic` files: on macOS, convert first using the built-in `sips` tool; elsewhere, skip with a clear message telling the user to export as JPEG.
- Auto-rotates based on EXIF orientation.
- **Crops to a square** using sharp's `attention` strategy (which tends to center on faces and people). Provide `--position center|top|attention` to override when a crop goes wrong, plus `--file <name>` to reprocess a single image.
- Resizes to **800×800**, JPEG quality ~80.
- **Strips all metadata, including GPS location.** These are family photos going into a GitHub repo, even a private one.
- Names output files by a short content hash (e.g. `a3f9c2e1.jpg`) so re-running never creates duplicates, and reports any it skipped as already present.
- Writes to `PHOTOS_DIR` when set, otherwise `photos/`.
- Creates the theme folder if it doesn't exist.
- After success, moves originals to `incoming/done/` (also gitignored) rather than deleting them.
- Supports `--dry-run` to show what would happen.
- Prints a summary: processed, skipped, failed.

`incoming/` and `photos/` (except `photos/README.md`) are in `.gitignore`. No images are ever committed.

## 10. README contents

- What the game is, in two sentences.
- Requirements (Node LTS) and `npm install` / `npm start`.
- How to join: scan the QR code, or type the URL, or share it.
- **Bring your own photos:** the repo contains none. Try it first with `npm run demo`, then add your own themes (section 9 workflow), optionally keeping them outside the repo with `PHOTOS_DIR`.
- A short privacy note: photos stay on your computer and your home network; the game never uploads them anywhere.
- License (pick one, e.g. MIT) and a line that the collection is part of A Reflection of You.
- Troubleshooting:
  - Both devices must be on the same WiFi network, not a guest network.
  - Some routers block devices from seeing each other ("client isolation" / "AP isolation"); turn it off or use the main network.
  - On first run, macOS may ask whether Node can accept incoming connections: choose **Allow**. If it was denied, re-enable it in System Settings → Network → Firewall.
  - If the IP-based URL changes from day to day, use the `.local` URL instead.
  - A shared link only works for someone already on the home WiFi.

## 11. Tests

Using `node:test`, at minimum:
- **Deal:** correct count, all distinct, identical order for both players, drawn only from the selected theme; Everyone draws across themes.
- **Random secrets:** always on the board, always different from each other.
- **Choosing:** locked secrets cannot change; play doesn't start until both are locked.
- **Privacy:** a player's state payload never contains the opponent's secret or flips.
- **Validation:** out-of-range indices, bad counts, and wrong-phase actions are rejected.
- **Layout:** spot-check the grid function for 6 and 24 faces on phone portrait, phone landscape, and iPad landscape sizes.
- **Themes:** folder scan ignores dotfiles, non-images, and empty folders; honors `PHOTOS_DIR`; returns an empty list cleanly when no photos exist.
- **No photos in git:** `git ls-files photos` returns only `photos/README.md`.
- **Demo:** `npm run demo` creates a playable `demo` theme of at least 24 images.
- **Prep script:** given a sample landscape image with EXIF GPS data, output is 800×800 with no metadata.

Manual testing will be done on real iPhones and iPads.

## 12. Acceptance checklist

- [ ] `npm start` prints the IP URL, the `.local` URL, and a terminal QR code.
- [ ] An iPhone and an iPad on the same WiFi can both join by scanning the QR code.
- [ ] Share button opens the iOS share sheet with the join URL.
- [ ] Setup offers theme, 6–24 face count, and Random / Players choose.
- [ ] Both devices show the same faces in the same order; each player's flips are invisible to the other.
- [ ] Secret face is locked at start and visible only via "My face."
- [ ] Reloading a device restores its seat, board, flips, and secret.
- [ ] New Game requires confirmation and resets both players.
- [ ] Board fits the screen without scrolling on an iPhone at 24 faces (or scrolls gracefully if tiles would be too small).
- [ ] Adding a new folder to `photos/` (or `PHOTOS_DIR`) makes a new theme appear with no code changes.
- [ ] A fresh clone with no photos shows the friendly "No photos yet" screen; `npm run demo` makes it playable.
- [ ] No image files are tracked in git.
- [ ] Prep script turns Photos exports into square, 800px, metadata-free JPEGs in the named theme folder.
- [ ] No network requests leave the local network.

## 13. Out of scope (for now)

- Remote / internet play (would need a hosted real-time server and room codes; the design should not preclude it, but don't build it).
- Photo tags, names, or attributes.
- Guess checking, scoring, win tracking, or turn enforcement.
- More than two players or spectators.
- Accounts, persistence across server restarts, sounds, animations beyond a simple flip.
